# Docs Site Crawl — 문서 사이트 구조적 순회

사용자가 "이 사이트 분석해서 내용 파악해줘"라고 하면 홈페이지 한 장만 읽고 끝내지 않는다. **왼쪽 네비게이션(또는 사이트맵)의 모든 섹션을 따라가며** 전체 문서를 구조적으로 파악한다.

## 왜 이 방식인가

문서 사이트의 정보 대부분은 첫 페이지에 없다. 영상 리뷰와 교차 검증하려면 기능 페이지 단위의 사실과 URL이 필요하다. 또 Mintlify·GitBook·Docusaurus 같은 최신 문서 프레임워크는 SSR로 HTML에 본문이 포함되는 경우가 많아 WebFetch만으로 충분하다 — "문서 사이트는 브라우저 자동화가 필요하다"는 가정부터 경계한다.

## 워크플로우

### Step 1: 전체 지도 확보 (순서대로 시도, 앞것이 성공하면 다음은 생략)

1. **`{site}/sitemap.xml`** — 최우선. 전체 URL 목록을 한 번에 얻는다. 경로 접두(`/help/`, `/changelog/`…)로 섹션을 그룹핑한다.
2. **`{site}/llms.txt`** — Mintlify 등 최신 프레임워크가 제공하는 LLM용 인덱스. 섹션 구조와 페이지 설명이 담겨 있을 때가 많다.
3. **홈페이지 HTML에서 nav/사이드바 링크 추출** — 위 둘이 없을 때. 순회 중 새 하위 링크를 만나면 목록에 계속 추가한다(외부 도메인 제외).

프레임워크 감지 힌트: 응답에 `mintcdn.com` → Mintlify, `/llms.txt` 존재 → 대부분 Mintlify, 정적 사이드바 마크업 → Docusaurus/VitePress 계열. 감지 결과는 분석 JSON의 `site.framework`에 기록한다.

### Step 2: 페이지별 순회

- WebFetch로 페이지별로 fetch하며 "이 페이지의 핵심 기능·설명·제약·제품명을 요약"을 수행
- **동시 호출은 3~5개 이하로 배치** 한다 (429 방지 — 남은 페이지는 앞 배치 완료 후)
- 순회 순서는 nav 순서(사용자 관점 구조)를 따른다
- WebFetch는 크로스호스트 리다이렉트를 따라가지 않고 반환하니, 안내된 새 URL로 다시 호출한다

### Step 3: 구조화

사이트 분석 JSON으로 정리한다. 다른 하네스에서 이 스킬을 단독 사용할 때도 같은 구조를 권장한다:
`nav_map`(섹션→페이지→요약) + `facts`(URL이 붙은 사실) + `features_documented` + `pages_failed`.
정확한 스키마는 `../research-synthesis-report/references/source-schemas.md`의 "Site Analysis" 참조.

## 페이지당 요약 정책

- 1~3문장 요약 + 기능 단위 사실. 원문 전사 금지
- 제약(가격, 지원 OS/브라우저, API 제한, 프라이버시·보안 정책)은 반드시 수집 — 리뷰 검증의 핵심 재료
- changelog가 있으면 최신 항목과 날짜를 기록한다

## 에러 대응

| 상황 | 대응 |
|------|------|
| WebFetch가 내용을 못 가져옴 (JS 전용 렌더링) | `mcp__web_reader__webReader`로 1회 재시도 → 계속 실패 시 `pages_failed`에 기록 |
| sitemap 없음 + nav도 JS 렌더 | 접근 가능한 페이지만 수집하고 한계를 결과에 명시 |
| 다른 도메인으로 리다이렉트 | 새 도메인으로 Step 1부터 재시도 |
| 페이지 100개 초과 | 섹션 대표 페이지 우선, 생략 목록을 명시 (침묵하는 누락 금지) |

## 테스트 시나리오

### 정상 흐름
1. Mintlify 문서 사이트 입력 → sitemap.xml에서 18개 URL 확보
2. 섹션별 그룹핑 후 3~5개 배치로 순회 → nav_map 완성
3. 결과: 페이지별 요약 + URL이 붙은 facts

### 에러 흐름
1. sitemap.xml 404 → llms.txt 404 → 홈페이지 HTML에서 nav 링크 추출로 전환
2. 일부 페이지 empty-render → pages_failed 기록 후 나머지로 완성
