# 종합 리포트 집필 가이드 (report-synthesizer용)

## 제1원칙 — 독자가 처음 읽어도 이해된다

리포트는 하네스 내부 자료가 아니라 독자가 읽는 문서다. 독자는 소스 JSON의 구조도, V1/V2 같은 내부 코드도, 검증 용어도 모른다. **추적 가능성은 유지하되 읽기 흐름 밖으로 보낸다.**

## 기본 골격 (질문 우선 구조)

리서치 질문이 목차를 결정한다. 아래는 기본 골격 — 질문 구성에 따라 3~5장을 분해·병합하라:

1. **한눈 요약 (Executive Summary)** — 리서치 질문 각각에 2~4문장 직접 답변. 결론 먼저.
2. **소스 및 방법** — 어떤 영상·문서를 분석했는지, 무엇이 누락되었는지 (신뢰도 투명성). **별칭 컬럼 포함** — 이 표가 본문 자연어 지칭의 기준이 된다
3. **제품/주제 개요** — 공식 문서 기준 베이스라인. 문서가 규정하는 대로.
4. **주제별 심층 분석** — 기능·논점 주제별: 리뷰 주장 종합 + 문서 대조 (확인/상충/미확인)
5. **리뷰어 관점 비교** — 영상 간 일치/분기. 어떤 평가가 consensus이고 어떤 것이 한 리뷰어의 취향인지
6. **주장 검증 표** — 논점별 대조표 (원문 대조의 중심지)
7. **장단점 종합** — 근거가 드러난 pros/cons
8. **미해결 질문·주의점** — 소스가 답하지 못한 것, 상충 해소에 필요한 추가 확인
9. **부록** — 소스별 한눈 표, 주요 타임스탬프 딥링크 목록

brief의 audience가 입문자면 3장 앞에 배경 설치를 추가하고, 전문가면 3장을 압축한다.

## 출처 표기 — 독자 우선 체계 (필수)

### 본문 — 자연어 지칭

- 소스는 **이름으로 부른다**: "개발동생 리뷰는", "Jay Choi는", "공식 문서는", "세 리뷰 공통으로", "두 리뷰는"
- 첫 언급은 소스 표의 정확한 이름, 이후 짧은 별칭 (별칭은 2장 소스 표에 등재)
- **본문에 내부 코드 금지** — 다음은 전부 반례다:
  - `[V1 7:39]`, `[Docs:subscription]` 같은 태그
  - "V1은 갈아탄 결정적 이유로 꼽았다" 식의 코드 주어
  - "conflict 표 참조", "fact pack" 같은 내부 용어
- 출처는 주어·서술에 녹인다:
  - 나쁜 예: "로그인 상태를 그대로 쓴다 [V2 2:57]"
  - 좋은 예: "Jay Choi의 리뷰는 브라우저 자체이므로 별도 연동 없이 로그인 상태를 그대로 쓴다고 짚는다"

### 각주 — 원문을 확인하고 싶은 독자의 자리

직접 인용, 계량 수치, 판정이 갈리는 주장처럼 원문 대조 가치가 높은 곳에만 각주를 단다:

- 본문: `문장[^1]` — 마커는 문장 뒤 (마침표 앞)
- 문서 끝 정의: `[^1]: 개발동생 리뷰 7:39 — [영상 위치](https://youtu.be/…?t=459)`
- **모든 문장에 다는 것이 아니다.** 문서당 20~40개 수준. 나머지 주장의 원문 대조는 '주장 검증 표'(6장)와 부록 딥링크 목록이 담당한다
- 각주 정의는 문서 맨 끝에 모은다 (렌더러가 각주 블록으로 묶어 출력)

### 표 — 축약 코드 허용, 범례 필수

'주장 검증 표'처럼 셀 공간이 필요한 곳에서만 소스 축약을 쓸 수 있다. 표 바로 위에 범례 한 줄:

> **출처 범례** — 개발동생 리뷰 · Jay Choi 리뷰 · 로치 리뷰 · 공식 문서

(리뷰가 많아 축약이 필요하면 소스 표의 별칭을 재사용: "개발동생(8/15)" 등)

### 용어 — 독자의 언어로

| 내부 용어 | 본문 표기 |
|-----------|-----------|
| confirm / conflict / unverified | ✅ 확인 / ⚠️ 상충 / ❓ 미확인 |
| 병기 | "양쪽을 나란히 실었다". ⚠️ 블록 라벨은 "공식 문서에 없는 내용" |
| ~장의 conflict 표 | "주장 검증 표" (장 번호 자체는 목차 기준으로 OK) |
| claim, fact, stance | "주장", "공식 문서의 설명", "입장" |
| caption의 "V1 —" | 채널명 — "개발동생 리뷰 — 실행 화면 (1:35)" |

## 교차 검증 표기

주제별 섹션에서 각 논점을 3값으로 판정한다:

| 판정 | 의미 | 표기 |
|------|------|------|
| 확인 | 문서가 리뷰 주장과 일치 | ✅ |
| 상충 | 양쪽이 다름 — **삭제 금지, 양쪽 표기** | ⚠️ |
| 미확인 | 문서가 침묵 (리뷰만 주장) | ❓ |

상충에는 가능한 원인(버전 차이, 시점 차이, 리뷰어 오류)을 한 문장 붙인다.

## 합성 문체

- **종합 후 서술**: "세 리뷰 모두 X를 지목했다" — 개별 영상 리캡이 아니라 합쳐진 문장
- 하나의 목소리: 중계 기사체 금지. 주어는 사실이지 리뷰어가 아니다
- 다만 평가의 주체가 중요할 때(한 리뷰어만의 취향, 유일한 반대 의견)는 리뷰어 이름을 밝힌다
- 한국어로 작성. 고유명사·기능명은 원어 그대로 (예: UltraBrowse, side panel)
- 소제목은 정보형 ("무엇이 좋다고 했나" > "장점")

## 분량 감각

- 소스 3~4개 기준 본문 3,000~6,000자(한글) 수준이 첫 드래프트 목표 — 리서치 질문 수와 소스 밀도에 비례해 조정
- 원문 대조 가치가 있는 주장을 선별해 각주·표로 보낸다 — 전부 본문에 실지 않는다

## 금지 사항

- **본문의 내부 코드·태그 노출** (`[V* …]`, `[Docs:…]`, "V1은", confirm/conflict 영문 라벨) — 발견 시 QA가 blocker로 처리한다
- 출처 없는 일반화 ("사람들은 ~라고 생각한다")
- 상충 은폐·임의 판정
- 문서에 없는 스펙 추측
- 소스 리캡 나열 ("첫 리뷰는 …했다. 두 번째 리뷰는 …했다.")
