# 슬라이드덱 기획 가이드

`deck-planner`가 `03_deck_plan.json`을 만들 때 따르는 원칙.

## 1. 발표 순서 ≠ 이해 순서

발표자는 **자기 연구 서사**로 말한다(내가 무엇을 했는가). 보고서 독자는 **이해 서사**가 필요하다(이게 왜 문제이고, 왜 그 해법인가). 둘은 자주 어긋난다.

전형적 재배열:

| 발표에서 | 보고서에서 |
|---------|-----------|
| 초록·목차를 먼저 | 문제의 실감부터 (왜 어려운가를 한 장면으로) |
| 배경 지식을 앞에 몰아서 | 그 지식이 필요해지는 슬라이드 **직전**에 배치 |
| 기여(contribution)를 먼저 선언 | 기여는 각 파트 끝에서 "그래서 무엇이 달라졌나"로 |
| 실험 세팅 → 결과 | 결과를 먼저 보여주고 세팅은 노트로 |
| 한계를 마지막에 한 장 | 각 접근의 한계를 그 접근 직후에 |

단, 재배열해도 각 슬라이드에 원문 타임스탬프를 남겨 독자가 원본과 대조할 수 있게 한다.

## 2. 난이도 사다리

기술 세미나 보고서가 실패하는 지점은 대부분 **한 슬라이드에서 난이도가 급상승할 때**다. 다음 규칙으로 방지한다.

- **용어 예산**: 슬라이드당 신규 전문 용어 최대 2개. 초과하면 앞에 `prereq` 슬라이드를 삽입한다.
- **의존 검사**: 각 슬라이드가 전제하는 개념이 앞에서 이미 나왔는지 확인한다. 안 나왔으면 `prereq`를 넣거나 순서를 바꾼다.
- **되짚기**: 섹션 도입 슬라이드에서 "여기까지 확보한 것"을 한 줄로 되짚는다.

## 3. 섹션 리듬 (3박자)

각 섹션은 다음 3박자를 유지한다.

1. **도입** (`section` 또는 `problem`) — 이 섹션이 답하는 질문 한 개
2. **전개** (`prereq` → `concept` → `architecture`/`math` → `demo`/`result`)
3. **정리** (`takeaway`) — 한 줄 결론 + 다음 섹션으로의 다리

## 4. 비주얼 배분

**원본이 있으면 원본을 쓴다.** 재현 다이어그램은 왜곡 위험이 있고, 독자는 "발표에서 실제로 본 것"을 신뢰한다.

| 상황 | 선택 |
|------|------|
| 화자가 슬라이드/그래프/사진을 보여줌 | `frame` |
| 실험 장면, 하드웨어 실물, 데모 영상 | `frame` |
| 정량 결과 그래프·표 | `frame` (읽히지 않으면 표로 재작성 + `html_body`) |
| 화자가 말로만 설명한 파이프라인/구조 | `diagram` |
| 좌표계·기하·힘 방향 등 공간 개념 | `diagram` |
| 수식의 각 항이 무엇을 뜻하는지 | `diagram` (equation) |
| A vs B 대비, before/after | `diagram` (comparison) |
| 연구 흐름·타임라인 | `diagram` (timeline) |
| 보고서 독자를 위해 새로 만든 요약 지도 | `diagram` |

프레임이 존재하지만 **읽히지 않는 경우**(저해상도 텍스트, 작은 그래프)는 프레임을 그대로 쓰지 말고, 같은 내용을 diagram으로 다시 그리거나 표로 옮긴다. 흐릿한 스크린샷은 보고서의 신뢰를 떨어뜨린다.

## 5. diagram_spec 작성

`visual-producer`가 codex에 넘기는 발주서다. 애매하면 codex가 지어낸다.

```json
{
  "slug": "pipeline-pose-estimation",
  "kind": "flow",
  "intent": "촉각 이미지 한 장에서 물체 자세 확률분포를 얻고, 시간에 따라 필터링해 추정을 좁히는 과정을 보인다",
  "elements": [
    "좌→우 4단계 박스: 원시 촉각 이미지 / 이진 접촉 패치 / 자세 확률분포(격자) / 필터링된 추정",
    "3→4단계 사이에 '시간 축 융합'을 나타내는 되먹임 화살표",
    "각 박스 아래 입출력 자료형 라벨"
  ],
  "labels_ko": ["원시 촉각 이미지", "이진 접촉 패치", "자세 확률분포", "필터링된 추정", "시간 축 융합"],
  "must_not": ["구체적 정확도 수치", "실제 논문 그림의 모방", "브랜드 로고"],
  "context": "발표 32:10 구간. 화자는 단일 이미지로는 자세가 모호하고(대칭성), 여러 시점을 융합해야 좁혀진다고 설명함.",
  "width": 1080,
  "height": 520
}
```

**`slug` 명명:** `{종류}-{주제}` 케밥 케이스. 슬라이드 ID를 쓰지 않는다 — 슬라이드가 재배열돼도 그림은 그대로 재사용된다.

**`must_not`에 반드시 넣을 것:** 근거 없는 수치, 원 논문 그림의 직접 모방, 실제로 확인하지 않은 하드웨어 형상.

## 6. 분량 규율

| depth | 슬라이드 수 | 다이어그램 |
|-------|-----------|-----------|
| `standard` | 30~45 | 8~15 |
| `deep` | 45~60 | 12~22 |

60장을 넘으면 슬라이드를 늘리지 말고 **내용을 해설 노트로 내린다.** 덱은 뼈대, 노트가 살이다. 슬라이드를 늘리면 독자가 길을 잃고, 노트를 늘리면 필요한 사람만 읽는다.

## 7. 근거 연결

모든 슬라이드는 `fact_ids`(ledger) 또는 `research_refs`(pack) 중 하나 이상을 참조해야 한다. 둘 다 없으면 그 슬라이드는 어디서 온 내용인지 아무도 모르며, QA가 삭제 대상으로 표시한다.

예외: `cover`, `agenda`, `section`, `takeaway`는 구조 슬라이드이므로 근거 참조를 요구하지 않는다.
